# أهداف الخدمة (SLO) — سوقنا MVP

## التوافر والأداء
| المؤشر | الهدف الأولي | ملاحظة |
|---|---|---|
| توافر `/api/v1` | 99.5% شهريًا | بيئة Staging قبل الإنتاج |
| قراءات إعلان (GET `/listings/{id}`, `/users/{id}`) | p95 < 300ms | كاش Redis للتصنيفات والملفات العامة |
| بحث `/listings` | p95 < 600ms | FTS عربي + trgm؛ قياس تحت 100k إعلان |
| رسائل (POST `/conversations/{id}/messages`) | p95 < 400ms | إدخال + تحديث عدّاد + Outbox |
| رفع صورة `/media` | p95 < 3s استلام، معالجة < 30s | Queue |

## الموثوقية
- **PITR** على Postgres المُدار (استعادة لأي نقطة خلال 7 أيام) + نسخة يومية مشفرة خارج المزود (احتفاظ 35 يومًا).
- **اختبار استعادة موثق** قبل الإطلاق: استعادة كاملة إلى بيئة معزولة خلال < 60 دقيقة (RTO)، فقدان ≤ 5 دقائق (RPO).
- **Outbox**: لا يُفقد إشعار/فهرسة عند تعطل المستهلك — إعادة محاولة بأسّية ثم `failed_jobs`.
- **Idempotency**: إعادة POST بنفس `Idempotency-Key` تعيد الرد المخزن خلال 24 ساعة.

## المراقبة
- Sentry للأخطاء، سجلات JSON مع `request_id`، Horizon dashboard للطوابير.
- تنبيهات: أخطاء 5xx > 1% لمدة 5 دقائق، طابور > 1000 مهمة معلقة، مساحة قرص < 15%.
- لا بيانات حساسة في السجلات: لا كلمات مرور، لا توكنات، لا نص رسائل.

## معايير قبول MVP (Go-live)
1. دورة الثلاثة أدوار تمر طرف-لطرف على Staging: مستهلك يسجل+ينشر، مشترٍ يراسل، تاجر يوثق من الإدارة، إدارة تراجع بلاغًا وتعلق مستخدمًا.
2. صفر فشل في مصفوفة الصلاحيات (IDOR) واختبارات Idempotency.
3. استعادة نسخة احتياطية ناجحة وموثقة.
4. Lighthouse/كفاءة: أحمال صفحة أولى < 2s على 3G مُحاكى (يعتمد على تحسينات Flutter لاحقًا).
5. كامل الـAPI موثق في `docs/api/openapi.yaml` ومفحوص بعقد (contract tests) في CI.
